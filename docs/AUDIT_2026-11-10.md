# CI、性能、体积、内存与安全检查

检查日期：2026-11-10。基线提交：`b86936c8f000fe00267550facb8ab690e85fb9bb`。主要范围是当前 Go + MyGo 原生版；旧 Tauri 代码只检查了 CI 的触发范围。本文区分实测结果、静态分析与后续建议。

## 后续按优先级落实（同日，尚未发布）

1. **采集端裁剪**：新增 SPF2 帧与有确认的 crop 命令。帧携带选区原点、原始屏幕尺寸和裁剪代次；确认后丢弃旧帧，来源尺寸变化中止采集。Linux 按 CPU/DMA-BUF 原始 stride 只写出选区；Windows 使用选区大小的 staging texture 和 CopySubresourceRegion，减少 GPU→CPU 复制。指针输入仍用原屏幕坐标。Linux 原生组件已编译和测试，Windows C++ 改动尚待 Windows SDK CI/真机验证。
2. **统一内存边界**：普通图片、截图解码和 OCR 统一 32 MP / 32768 边长，解码前先查尺寸；文件读取 220 MiB 上限，拒绝普通文件以外的来源。采集保持 16384 边长，拼接保持 24 MP / 30000px。多窗口解码、候选图片与后台持有通过租约共享 512 MiB 估算预算，每图计 `13×像素数+64 KiB`，覆盖原图、显示副本和一个处理缓冲的估计开销；失败、被丢弃的 UI 投递、窗口关闭和后台结束均释放。长截图在开始滚动前按最大拼接像素预留结果预算，完成后原子缩减到实际尺寸，避免完成时被其他图片抢占额度；取消时释放预留。它不是进程 RSS 硬上限：编码数据、正在采集的帧、拼接缓存、标注、驱动和 OCR 子进程另行占用。小选区会脱离大原图的底层数组。
3. **撤销历史**：80 步之外增加每窗口 32 MiB 的保守字节预算，包含点集容量、文字和结构体，跨快照共享也按每份估算。丢弃最旧历史并清空引用，不删除当前文档；当前文档本身不受这个历史预算限制。
4. **组件与供应链**：移除当前目录/祖先 `go.mod` 查找。显式覆盖要求绝对路径且不再回退，避免测试误用旧安装。六种外部 Actions 已查询 GitHub API 并固定到真实提交 SHA；保留现用 major，尚未完成 Node 24 Action major 升级。OCR 跨平台哈希锁包含平台传递依赖，`uv pip sync --require-hashes --only-binary :all:` 精确同步构建环境。附带 Python 分发依赖的 CycloneDX 清单与源码/锁文件哈希；打包校验拒绝混用旧源码、锁文件、采集协议或遗漏许可证。新增每周 Go/Python 扫描和 Dependabot 配置；远程定期扫描的执行结果以 Actions 记录为准。
5. **词块扫选**：拖动连续选择/取消，以手势起点决定模式；相邻采样点间做矩形相交检查，快速移动不会跳过中间词。保持点选、Shift 和键盘切换；仅命中虚拟列表可见部分，进度更新和模式切换终止旧手势，关闭时释放命中句柄。

## CI 失败原因与本次修复

GitHub Actions 的发布任务 `42597713960`（2026-11-09，`v0.2.1`）中，native、四个平台组件和 Arch 构建全部成功，只有 publish 失败：

```text
AssertionError: Missing/empty installer: screenpin-native-0.2.1-1-x86_64.pkg.tar.zst
```

`mygo.json` 与 `internal/desktop/launch.go` 是 `0.2.1`，`packaging/arch-native/PKGBUILD` 的 `pkgver` 却仍是 `0.2.0`。分支构建没有检查各个平台的最终附件集合，因此同一提交的原生预览任务 `42597660818` 能成功，发布任务在所有包完成后才发现版本不一致。最慢的 Intel macOS job 用时 9 分 30 秒。

更早的任务 `42597066048` 在 macOS 上失败于 `TestSettingsTabsShareDraftAndKeepSaveVisibleAtMinimumSize`，原因是测试点击了该平台不支持的长截图开关；基线提交已经修复这个测试。最新失败不需要再次修改 macOS 测试。

本次落地的改动：

- 将原生 Arch 配方版本修正为 `0.2.1`。
- 为全部原生构建添加前置检查：MyGo 版本、Go 程序版本、Arch 版本必须一致；标签构建还检查标签和非空发布说明。Arch 附件名读取实际 `pkgrel`。
- 保留七个附件完整性检查，拒绝缺失、空文件、软链接与多余文件。将发布校验中的 `assert` 改为显式错误，避免 `python -O` 跳过这些检查。
- 新增八项回归测试，覆盖此次版本漂移、旧版本附件、错误标签、缺失发布说明、包修订号、空包/额外文件及优化模式。
- 给构建和发布设置超时；同一分支的新原生构建取消旧任务，标签发布不自动取消；发布只下载当前 SHA 的原生构建附件。
- 旧 Tauri Arch 工作流仅在相关源码、依赖、配方或工作流变化时运行，保留手动触发与 `v0.1.*` 标签触发。
- README 的 Go 最低版本修正为 `go.mod` 要求的 `1.27.3`。

日志还提示部分 Actions 使用 Node 20，运行器已强制切换到 Node 24；这是后续升级事项，此次失败日志的直接原因是 Arch 附件版本。

本次没有提交、推送、移动标签或发布 Release。检查时 `v0.2.1` Release API 返回 404。修复进入仓库后，应在包含修复的新提交上触发构建；旧任务重跑仍使用原始 SHA。建议下次正式发布统一更新三个原生版本入口和发布说明，再创建新版本标签，避免改写已有标签。

## 性能：已优化分配，主要开销仍是像素处理

本地环境：Linux amd64，Go `1.27.3-X:nodwarf5`，Intel Core Ultra 7 265KF。使用已有 benchmark，未改动识别或拼接判定阈值。

| 测量 | 修改前 | 修改后 |
| --- | ---: | ---: |
| `BenchmarkManualMovingViewport` 耗时 | 29.15 ms/op | 三次 28.01–30.44 ms/op |
| 同一基准分配量 | 16,051,060 B/op | 约 15,657,200 B/op |
| 同一基准分配次数 | 1,498 allocs/op | 46 allocs/op |
| 未变化画面控制器 | 174.7 µs/op，0 分配 | 171.5–174.0 µs/op，0 分配 |

这个移动画面基准包含控制器初始化和一次匹配，画面为 1358×1074，不能将其当作端到端截图延迟或每个后续帧的成本。基线仅测一次，耗时也有波动，因此没有足够证据声称速度明显提升。已确认的收益是分配次数减少约 97%，分配字节减少约 2.5%。

`internal/scrollshot/stitch.go` 的每个候选偏移原先各分配一个最多 28 元素的评分数组，现在在一次匹配内复用；同时按照实际偏移数预分配候选列表，避免扩容。现有像素准确性、固定栏、重复画面、反向滚动、撤销和竞态测试全部通过。

后续优先级：

1. **采集端先裁剪到选区，再传输像素。** `readPacket` 每个完整桌面帧都分配 RGBA，消费者之后才取选区。以 3840×2160、25 帧/秒推算，仅帧缓冲写入就约 791 MiB/秒，尚未计入拷贝和拼接；这是理论带宽，不是本次实测。优先减少传输面积，再设计有明确归还协议的缓冲池，避免复用仍被 `SubImage` 持有的内存。
2. **OCR 排队与选区分配已在后续改动中优化。** 使用 `RecognizePrepared` 在获得全局名额后才合成，框选后仅渲染选区并拥有独立像素缓冲。来源窗口本身仍持有原图；关闭来源会取消任务。另加入模型短时复用、原始 RGB 传输和词块交互，详见 [OCR 流程说明](OCR_WORKFLOW.md)。
3. **补充持续滚动和导出基准。** 当前匹配仍约 29 ms，临时数组只是小部分成本。用 CPU/heap profile 判断匹配、预览缩放、PNG 编码的占比，再选择优化；不要根据上述分配优化推断帧率提升。

打包过程也已优化：`scripts/package-release.py` 对安装包计算 SHA-256 改为每次读取 1 MiB，取消 `read_bytes()` 的整包临时内存。该实现兼容 Python 3.10。

## 内存：当前压力测试未观察到 Go 堆持续泄漏

复跑 `TestSoftwareImageLifecycleMemoryStress`：1920×1080，10 次预热后进行 80 次图片加载、软件渲染和关闭；刻意保留关闭后的编辑器对象。

| 完成轮数 | GC 后 Go 堆 | goroutine |
| --- | ---: | ---: |
| 20 | 0.89 MiB | 3 |
| 40 | 0.91 MiB | 3 |
| 60 | 0.93 MiB | 3 |
| 80 | 0.94 MiB | 3 |

所有图片像素的弱引用都已回收，轻微增长包含测试主动保留的已关闭编辑器对象。关闭清理、历史栈清空、采集队列清空及 OCR 排队取消的现有保护仍有效；真实 OCR 的中英文和长图测试通过。

这不等于排除所有平台泄漏：该测试没有原生窗口、GPU 纹理、GTK/D3D/Metal 驱动分配。应在各桌面重复进行 100 次截图/关闭、长截图取消、OCR 排队取消，比较预热后的空闲 RSS、Go live heap、goroutine、文件描述符/句柄、子进程数与 GPU 资源是否回到稳定区间。OCR 子进程独立退出，不代表主进程排队的合成图也没有内存峰值。

还需要统一容量策略：工程/导入图片限制为 100 MP，原生像素/OCR 为 32 MP，长截图为 24 MP；100 MP RGBA 单份约 381 MiB，解码转换、标注合成与多个窗口会叠加。建议在实际分配前设置一致的像素/字节预算，并同时限制待处理大图总量。80 步撤销上限是步骤数限制，并非笔迹字节预算。

## 安全策略与剩余边界

本次 `govulncheck` 返回 `No vulnerabilities found`，仅代表当前 Linux 配置下扫描到的 Go 代码和依赖没有命中已知问题，不覆盖全部 Windows/macOS 分支、Python wheels、OCR 模型、旧 npm/Rust 栈或原生系统库。

已经存在的有效保护：OCR 使用本地模型、缺失模型即报错；子进程直接执行组件路径而非拼接 shell；OCR 超时三分钟、输出和日志有上限；采集协议验证帧尺寸、格式和控制响应长度；Portal 令牌使用私有临时文件原子替换；发布前要求附件完整；构建默认只有 `contents: read`，仅发布 job 获得写权限。

| 优先级 | 证据与边界 | 建议与验收 |
| --- | --- | --- |
| P1 | Actions 使用可移动版本标签，Arch 使用 `archlinux:latest`；OCR 依赖锁了版本但没有下载哈希 | Actions 固定完整提交 SHA，由 Dependabot 更新；基线镜像固定 digest；为各平台 wheels 生成带哈希的锁文件。升级 Node 24 Actions 后重跑全部平台。 |
| P1 | `components.Find` 在安装组件缺失时会扫描当前目录祖先的 `go.mod` 并执行其 resources 下程序；环境覆盖目录也可优先加载 | 发布版只在安装资源目录找 worker；开发回退改为显式开发选项。安装损坏应清楚报错。该风险需要用户在不可信目录启动且缺失正常组件等前提，不是已证明的远程执行漏洞。 |
| P1 | Go/Python 解码输入虽有部分上限，但入口预算不一致；Portal 与 macOS 截图读取使用 `os.ReadFile` | 在统一读取/解码入口同时限制编码字节与解码尺寸，覆盖截断头、超大维度、畸形图片、损坏协议；对协议和图片入口做持续 fuzz。 |
| P1 | 当前 macOS 是 ad-hoc 签名，SHA256SUMS 随 Release 一起发布；校验和不能单独证明发布者身份 | 发布流水线生成 SBOM/来源证明；配置 Developer ID、公证与 Windows 签名时将凭据限定在发布 job/environment，普通 PR 构建不接触签名凭据。 |
| P2 | “离线 OCR”是应用行为约定，普通子进程仍继承用户权限与网络能力 | 清理不需要的环境变量，并评估系统级无网络、低权限沙箱；需跨平台验证模型和动态库加载。不要将进程分离表述为安全沙箱。 |
| P2 | 当前工作流没有定期依赖漏洞检查和供应链清单 | 定期扫描 Go、Python 及仍维护的旧依赖栈，明确严重性门槛和处理周期；原生库也纳入 SBOM，防止只扫描 Go 后误判整个应用安全。 |
