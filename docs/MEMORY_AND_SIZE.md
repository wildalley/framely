# 内存与包体积检查（2026-11-07）

## 内存结论与修复

没有从 Linux 本地 Go 堆、软件渲染循环和 OCR 子进程测试中观察到持续增长的泄漏。检查发现并修复了三处不必要的数据保留：

- 撤销后只缩短切片，底层数组仍持有已弹出的标注及笔迹。现在清空撤销/重做栈中已消费的槽位。旧实现能复现弱引用回收失败，新实现通过同一测试。历史仍保留最多 80 个有效步骤。
- 长截图每次刷新都创建新位图，框架会缓存旧纹理若干帧。现在使用固定大小的纹理并通过 `Bitmap.Update` 更新，用源区域绘制保持不同长宽比，避免长图持续增长时反复创建纹理。
- 采集流关闭时，其单元素队列仍可能持有完整桌面帧。现在关闭后清空队列，并拒绝继续取帧。32 MP RGBA 帧最多约 122 MiB，不需要一直留到预览窗口关闭。

另限制整个应用同时只运行一个 OCR 子进程，其他图片的识别请求排队，关闭图片可以取消排队。一次 OCR 会加载独立的模型和运行库，多窗口同时识别原先会叠加这些内存。

## 本地测量

- 1920×1080 图片，10 次预热后再执行 80 次像素加载、软件渲染及关闭；回收后的存活 Go 堆依次约为 0.82、0.83、0.85、0.87 MiB，goroutine 一直为 3。测试刻意保留关闭后的编辑器对象，所有图片像素弱引用仍可回收。
- 旧版和精简版 OCR 各执行 6 次真实中英文识别；每次任务结束进程均退出。旧版峰值 RSS 约 196–213 MiB，精简版约 192–199 MiB。不同进程之间的几 MiB 波动不能据此认定泄漏或显著的运行内存优化。
- 精简组件通过中英文图片和 2000×2200 横纵分块图片识别测试；三个 ONNX 模型逐字节保持一致。
- Linux 本地完整竞态测试、静态检查及应用包内 OCR 测试通过。

本测量不包含真实原生窗口及 GPU 驱动分配，不能据此排除 GTK、D3D、Metal 或驱动中的泄漏。Windows/macOS 的包内识别由各自 CI 构建验证，也不能代替长期桌面压力测试。进程 RSS 未立即下降可能来自运行时保留可复用内存；判断 Go 堆泄漏时应比较 GC 后仍可达的对象。

复现 Go 堆检查：

```bash
mkdir -p build/memory-audit
SCREENPIN_MEMORY_AUDIT=1 \
SCREENPIN_MEMORY_PROFILE_DIR="$PWD/build/memory-audit" \
go test -count=1 -run TestSoftwareImageLifecycleMemoryStress -v ./internal/editor
go tool pprof -top build/memory-audit/editor-heap.pprof
```

测试也已加入 Linux CI。普通 `go test` 会跳过这项压力测试。

## 完整离线包瘦身

包体主要来自 OCR，Linux 主程序约 13.7 MiB。原先 `--collect-all` 会收集 RapidOCR 的其他推理后端和 ONNX 的训练、转换工具。现在采用项目专用 PyInstaller hooks，只收集所需的 ONNX 推理模块、配置和全部现有模型。

Linux 还移除一份未被 Python 扩展链接的独立 ONNX C API 动态库；扩展自身已包含推理实现。构建时检查 ELF 依赖，若未来的 wheel 开始依赖该库就保留。Windows/macOS 保留原有动态库布局。

本地使用相同的 gzip 级别、目录结构和软链接保留方式测量 OCR 目录：

| 指标 | 旧版 | 精简版 |
| --- | ---: | ---: |
| 解压磁盘占用（`du`） | 约 354 MiB | 约 319 MiB |
| 文件内容大小（不重复计算软链接） | 351.8 MiB | 318.4 MiB |
| gzip 归档 | 149.2 MiB | 132.9 MiB |

OCR 归档减少约 16.3 MiB（10.9%）。这不是整个 DEB、DMG 或 EXE 的大小；最终收益取决于各平台运行库和安装程序压缩方式。CI 会打印每个最终附件的字节数。

这轮保留现有模型、依赖版本、离线能力和许可证。更大的缩减需要进一步替换或裁剪 OpenCV/Python 推理运行库，或提供可选 OCR 组件包；这些方案需要另做三平台兼容性和识别质量验证，不应直接删除现有库或量化模型后就宣称等效。

打包规则依据：[PyInstaller 项目专用 hooks 文档](https://pyinstaller.org/en/stable/hooks.html)。
