# 性能与内存检查（2026-11-12）

检查对象为本次提交的 Linux 源码，包括长截图与控件调整。测试机器为 Intel Core Ultra 7 265KF；耗时是本机软件路径的参考值，不代表其他平台或设备。

## 结论与修复

本轮未在图片窗口压力测试、长截图释放检查和原生窗口循环中发现持续增长的像素缓冲、文件描述符或 goroutine。发现并修复了两处长截图开销：

1. **侧栏缓存额外保留首张整帧。** 原实现即使只有窄侧栏也保留整张首帧；改为将左右侧栏复制到紧凑的独立缓冲，没有侧栏时不保留该缓存。960×760 视口、160 像素侧栏的样例从约 2.78 MiB 缩为 0.46 MiB。撤回与已发出的不可变预览仍保持正确生命周期。
2. **缩略图生成产生大量临时像素对象。** 分块图像仅实现通用 `At`，缩放时反复把像素装箱为接口值。增加按值返回的 `RGBA64At`，让 x/image/draw 使用专用路径。新增测试将优化结果与通用缩放逐字节比较，确保没有改变图像内容。

侧栏填充仍保留底部文字拖影修复：侧栏原图保留一次，新增高度填充背景色，不拉伸头像或文字。

## 性能实测

| 项目 | 耗时 | 分配 |
| --- | --- | --- |
| 长截图缩略图，优化前 | 31.97 ms/次 | 10,803,457 B/次，2,160,006 次分配 |
| 同一组缩略图，优化后 | 20.14 ms/次 | 2,162,976 B/次，5 次分配 |
| 桌面预览贴图更新（已有双缓冲） | 0.13 ms/次 | 96 B/次，1 次分配 |
| 4K 选区鼠标移动的软件渲染 | 1.62 ms/次 | 5,902 B/次，86 次分配 |
| 静止长截图控制器 | 0.17 ms/次 | 0 B/次，0 次分配 |
| 初始化并匹配一段滚动（1358×1074） | 28.00 ms/次 | 15,657,523 B/次，46 次分配 |

缩略图的临时分配约减少 80%，耗时约减少 37%。剩余约 2.16 MB 主要是缩略图输出像素，不是不断保留的历史副本。滚动匹配基准包含初始化、首帧复制和新帧匹配，不能将其全部视为每一帧的常驻开销。

采集解码基准中，800×1000 RGBA 帧约 0.73 ms、3.20 MB/帧；3840×2160 帧约 9.47 ms、33.18 MB/帧。这是原始像素大小造成的有界分配，仍会产生内存带宽及 GC 压力。采集代码使用单槽最新帧队列，区域采集尽量只传选区像素；本轮没有改动采集协议或加入可能延长像素寿命的对象池。

## 生命周期与释放

- **1080p 编辑器压力测试**：10 次预热后，再执行 80 次加载、软件绘制、样式面板、钉图及关闭。保留已关闭的 App 对象，通过弱引用检查原图是否回收。20/40/60/80 次后的 GC 后堆分别约 0.91/0.93/0.94/0.96 MiB，goroutine 始终为 3；原图均可回收。
- **长截图缓存**：弱引用验证侧栏缓存不再钉住原始整帧；20 轮拼接和 Release 后，即使保留 Stitcher 对象，当前视口和侧栏像素均可回收。已有撤回、上限、滚动条和固定侧栏像素回归通过。
- **原生窗口测试**：使用现有 `audit-native-lifecycle.go` 在真实 Linux 图形会话创建并销毁 120 个小窗口，只显示生成的 1080p 测试像素。20 次后的 RSS 为 238,484 KiB，120 次后为 238,172 KiB；文件描述符始终 52，goroutine 始终 4。预热后 RSS 约 233 MiB，未随窗口次数持续增长。该数值包含图形栈等原生分配，不能与 Go 堆混为一谈。
- **代码核查**：长截图关闭会取消任务、销毁控制窗口并清空预览双缓冲；拼接任务退出调用 Release。录屏 ticker 和采集进程在退出路径释放；原生编码器使用固定/最新帧缓冲，不把整段视频放进内存。OCR 进程池空闲 45 秒后回收，退出时关闭进程并等待清理。

2400 万像素的长截图限制不是整个进程的 RSS 上限：还需考虑撤回、采集中的视口、最终输出、预览、图形驱动以及 OCR 子进程。RSS 未立即下降也不直接说明泄漏，应结合 GC 后可达对象和反复操作后的增长趋势判断。

## 尚未覆盖
